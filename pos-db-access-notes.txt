CURRENT STATE (how data flows today)
------------------------------------------------------------------------------
- POS back-office app ("Office") exports a "Journal Log" as a semicolon-
  delimited CSV.
- CSVs are dropped into Google Drive (used as a go-between from the server to
  the desktop), then placed in this repo's data/ folder.
- Python ETL (scripts/export_dashboards.py, `npm run etl`) reads ALL CSVs,
  dedupes by (Transaction ID + Item ID), resolves modifiers, and writes JSON
  to public/data/ for the Next.js dashboard.

CSV fields the ETL relies on (semicolon-delimited):
  Transaction ID, Item ID, Name, Quantity, Unit Amount, Total,
  Item Created Date, Item Created Time, Department, Subdepartment,
  Item Type, Transaction Type, Deleted, Voided
Business-day rule: activity before 4:00 AM rolls to the previous day.
Modifiers: modifier revenue is rolled into the parent product (no double-count).

------------------------------------------------------------------------------
DECISION / PLAN (Path A: SQL login via Mixed Mode, applied on reboot)
------------------------------------------------------------------------------
STEP 1 (no disruption - can do anytime):
  In SSMS: right-click server (SYNCSERVER\SYNCDB) -> Properties -> Security ->
  select "SQL Server and Windows Authentication mode" -> OK.
  This only STAGES the change. NOTE: enabling Mixed Mode is ADDITIVE - it does
  NOT lock out the POS; Windows auth keeps working exactly as before. The change
  just needs a service restart (=> a reboot) to take effect.

STEP 2 (apply): Reboot the server (the normal Monday reboot works).
  After reboot, Mixed Mode is active. The SQL service auto-starts.

STEP 3 (after reboot): create a dedicated READ-ONLY SQL login (least privilege):

    -- run as current owner/sysadmin account
    CREATE LOGIN concourse_readonly
        WITH PASSWORD = 'PUT-A-STRONG-PASSWORD-HERE',
             CHECK_POLICY = ON;

    USE SyncJournal;
    CREATE USER concourse_readonly FOR LOGIN concourse_readonly;
    ALTER ROLE db_datareader ADD MEMBER concourse_readonly;

    USE Sync;   -- for lookup tables (item/department names) if needed
    CREATE USER concourse_readonly FOR LOGIN concourse_readonly;
    ALTER ROLE db_datareader ADD MEMBER concourse_readonly;

  db_datareader = SELECT on all tables/views, and NOTHING else (no insert/
  update/delete/schema). That is exactly the read-only box we want.

STEP 4 (verify the guardrail): reconnect as concourse_readonly (SQL auth) and:
    SELECT TOP 10 * FROM SyncJournal.sys.tables;        -- should WORK
    CREATE TABLE dbo.zzz_test (a int);                  -- should FAIL (denied)
  If the write FAILS, the read-only guardrail is correct. If it SUCCEEDS, stop -
  the grant was too broad.

STEP 5 (store secret safely): put the password in a password manager. When the
  Python pull is built, the password goes in an ENV VAR or a .gitignored .env -
  NEVER hard-coded or committed.

Alternative (Path B, not chosen): a dedicated Windows account (no Mixed Mode,
no restart), but creating a Windows user also needs local admin, and workgroup
pass-through auth makes desktop testing fiddly. Revisit only if Path A stalls.

NEXT STEPS AFTER THE READ-ONLY LOGIN EXISTS
------------------------------------------------------------------------------
1. SCHEMA DISCOVERY (read-only) - map SyncJournal tables to the CSV fields.
   Run in SSMS (all read-only / NOLOCK; safe):

     SELECT @@VERSION;

     SELECT name, state_desc, recovery_model_desc FROM sys.databases ORDER BY name;

     USE SyncJournal;
     -- tables by approx row count (find the big "sales" tables)
     SELECT s.name AS [schema], t.name AS table_name, SUM(p.rows) AS approx_rows
     FROM sys.tables t
     JOIN sys.schemas s    ON t.schema_id = s.schema_id
     JOIN sys.partitions p ON t.object_id = p.object_id AND p.index_id IN (0,1)
     GROUP BY s.name, t.name
     ORDER BY approx_rows DESC;

     -- all columns (match to: Transaction ID, Item ID, Name, Quantity,
     --   Unit Amount, Total, Item Created Date/Time, Department, Subdepartment,
     --   Item Type, Transaction Type, Deleted, Voided)
     SELECT t.name AS table_name, c.name AS column_name, ty.name AS data_type,
            c.max_length, c.is_nullable
     FROM sys.columns c
     JOIN sys.tables t ON c.object_id = t.object_id
     JOIN sys.types ty ON c.user_type_id = ty.user_type_id
     ORDER BY t.name, c.column_id;

SAFETY GUARDRAILS (non-negotiable)
------------------------------------------------------------------------------
- READ-ONLY identity only (db_datareader). Never automate under owner/sysadmin.
- SELECT-only while exploring; do NOT edit rows in SSMS grids.
- Run pulls OFF-HOURS; use READ UNCOMMITTED / WITH (NOLOCK) so we never lock
  live scoring/POS tables during service.
- Reconcile DB output vs manual export before cutover.
- Confirm SQL backups exist & work before relying on direct access
  (recovery model seen via sys.databases; verify a real backup job runs).
- Check with BRUNSWICK that direct read-only DB access is acceptable
  (possible support/warranty consideration). Also a good time to ask who holds
  local admin on SYNCSERVER.
- Don't brute-force around OS security or reboot mid-service. The recurring
  blocker is local admin on SYNCSERVER - get it properly or have the holder act.
- Flat/unregulated network + SQL Server = security smell; tighten over time
  (our pulls don't make it worse, but note it).
